# GaggiMate+

Native iOS client for the [GaggiMate](https://github.com/jniebuhr/gaggimate) espresso machine controller, an ESP32 board that exposes a local WebSocket API. Display name "GaggiMate+" (read "GaggiMate Plus"); code and repo name `GaggiMatePlus`.

## Stack

- iOS 27+, SwiftUI, Swift Testing. Xcode 27.2 (Swift 6.4), the same build GitHub-hosted CI uses; nell-remote's runners have Xcode 27.0 for now.
- Swift 6 language mode with complete strict concurrency, Approachable Concurrency, strict memory safety, and every upcoming feature Swift 6 mode does not turn on yet (`ExistentialAny`, `InternalImportsByDefault`, `MemberImportVisibility`, `InferIsolatedConformances`, `NonisolatedNonsendingByDefault`, `ImmutableWeakCaptures`). Set in `Project.swift`; no experimental features.
- Bundle ID `dev.niklashein.gaggimateplus`.
- The Xcode workspace is generated by Tuist from `Project.swift`; the Tuist version is pinned in `mise.toml`. The `.xcodeproj` and `.xcworkspace` are gitignored; run `tuist generate` after changing `Project.swift` or adding files.

## Modules

Every module is a static framework defined in `Project.swift`, with sources in `<Module>/Sources` and Swift Testing tests in `<Module>/Tests`. The `GaggiMatePlus` scheme runs all tests; each module with tests also has a scheme of its own (`testScheme(for:)`) and a `Test <Module>` CI job. A new test target needs both: the scheme in `Project.swift` and the module in the test matrix in `.github/workflows/ci.yml`. Every direct dependency:

```text
GaggiMatePlus (app) ──> UI / Navigation / Networking / DesignSystem / Models
UI                  ──> Navigation / DesignSystem / Models
Navigation          ──> (nothing)
Networking          ──> Models
DesignSystem        ──> (nothing)
Models              ──> (nothing)
ModelsTests         ──> Models
NavigationTests     ──> Navigation
NetworkingTests     ──> Networking / Models
```

- `App/`: the app target and composition root. It creates the Networking client, feeds its events into the store, and hands the store, the commands and the navigation coordinator to the UI through the environment. For now it creates only the coordinator.
- `Models`: Codable message types, machine state (including the partial `evt:status` merge), the `@Observable` store, and the command protocol that Networking implements.
- `Navigation`: the `@Observable` coordinator that owns all navigation, as in Nell. For now it holds the selected root (Brew or Machine) and whether the sidebar is open.
- `Networking`: the WebSocket client.
- `UI`: SwiftUI screens, and the shell: the sidebar behind the main screen, which pushes it aside. It never imports Networking; previews use fakes. Its colours are Display P3 sets in `UI/Resources/Colors.xcassets`, named for the colour (`Coral`), not its role; code uses Xcode's generated accessors (`.coral`), which are internal to the module that owns the catalog.
- `DesignSystem`: measurements, motion, typography and reusable styles.

## Build and test

Every command runs through `just` (see `justfile`); mise only pins tool versions (`mise.toml`). First time: `mise install`.

**Local CI:** `just ci`

- `just`: list recipes.
- `just lint`: SwiftLint in strict mode, so every warning fails (config: `.swiftlint.yml`, adapted from Mastermind's). Its custom "Tokens only" rules keep literal numbers, colours and fonts out of UI code; `DesignSystem` defines the values, and the asset catalog the colours.
- `just project`: generate the Xcode workspace with Tuist.
- `just build`: build the app for the simulator.
- `just test`: run every module's unit tests. `just test <Module>` (for example `just test Models`) runs one module's.
- `just ci`: local CI, the same steps as GitHub CI: `just lint`, `just build`, then `just test`. Run it, and make sure it passes, before creating or updating a pull request.
- Tests use an iPhone 18 Pro simulator named `GaggiMatePlus`, created if missing and left booted so test runs skip the boot. Override with `IOS_SIMULATOR=<name>` or `IOS_DESTINATION=<xcodebuild destination>`.

## Branches and releases

- `main` is protected: changes land only through pull requests, and GitHub CI must pass. Its `Lint` job runs `just lint`, `Build` runs `just build`, and each `Test <Module>` job runs `just test <Module>` on an iPhone 18 Pro simulator, so a failure names the module; the `CI` job, the required check, passes only when all of them do. No approving review is required: only the owner has write access, so only they can merge, and `CODEOWNERS` requests their review on contributor pull requests.
- Where CI runs: `Lint`, `Build` and `Test` run on nell-remote, the owner's always-on Mac, on four self-hosted runners (`nell-remote-1` … `nell-remote-4`, label `nell-remote`) under its `ci` account, with Xcode 27.0 until it gets 27.2. Each runner keeps a simulator of its own, `GaggiMatePlus-CI-<runner>`, booted between runs. Pull requests from forks run those jobs on GitHub's `xcode-27` image with Xcode 27.2 instead. The `CI` job and the other workflows run on GitHub-hosted Ubuntu. The runners are launchd services in `ci`'s user domain (`~ci/Library/LaunchAgents`), which `/Library/LaunchDaemons/dev.niklashein.gaggimateplus.ci-runners.plist` starts at boot.
- Every workflow run from an outside contributor waits for the owner's approval (fork pull request policy: all external contributors). A fork's pull request runs its own copy of the workflows and can point a job at `nell-remote`, so review its changes to `.github/` and to what CI runs (`justfile`, `scripts/`, `mise.toml`, `Project.swift`) before approving a run.
- Releases are cut by pushing a `v*` tag (for example `v1.0.0`) on a commit on `main`. The release workflow creates the GitHub release with generated notes.

## Commits and pull request titles

Every commit subject and every pull request title follows [Conventional Commits](https://www.conventionalcommits.org): `<type>: <description>`, optionally with a scope, `<type>(<scope>): <description>`. Write the description in lowercase and the imperative, with no trailing period: `feat: add the brew screen`, `fix(networking): retry the handshake`. Put `!` before the colon for a breaking change. The `Conventional Commits` check, required on `main`, enforces the format for a pull request's title and all of its commits (`scripts/check-conventional-commits.sh`). Squash merges use the title as the commit title on `main`.

- `feat`: a new feature.
- `fix`: a bug fix.
- `docs`: documentation only.
- `style`: formatting with no behaviour change.
- `refactor`: a code change that neither fixes a bug nor adds a feature.
- `perf`: a performance improvement.
- `test`: adding or fixing tests.
- `build`: the build system, project generation or dependencies (Tuist, mise, the justfile).
- `ci`: CI workflows and checks.
- `chore`: anything else that doesn't touch the app's code.
- `revert`: reverts an earlier change.

## GaggiMate WebSocket API

- Connect to `ws://<host>/ws`. No auth.
- JSON messages, typed by the `tp` field: `req:*` (client requests), `res:*` (responses), `evt:*` (pushed events).
- Requests and responses are correlated by `rid`.
- `evt:status` is PARTIAL:
  - Fast telemetry every 500 ms: `ct`, `tt`, `pr`, `pt`, `fl`.
  - Slow state is sent on change or at least every 10 s, and in full on connect.
  - Merge each frame onto the last known state: an absent key means keep the previous value, `null` means clear it.
- Spec source: <https://raw.githubusercontent.com/jniebuhr/gaggimate/master/docs/websocket-api.yaml>. Link it, don't vendor it: upstream is CC BY-NC-SA, this repo is MIT.

## Conventions

- The socket lives in an `actor` (Networking).
- UI state lives in an `@Observable` store (Models).
- Request/response uses async/await, keyed by `rid`.
- Reconnect with backoff when the connection drops.
